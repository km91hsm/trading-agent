## 2. 7번 — 2-O10 동시 판정

### 현재 경로
- 같은 계좌에 동시에 주문을 낼 수 있는 경로가 여럿이다. 분석 세션의 `trader tool` 서브프로세스, 재평가 레인(heavy 락 없음, 종목 락만), 단타(heavy 락 무관), 리밸런스·헤지·현금 ETF·손절(monitor 경로), 웹·텔레그램·CLI 승인이다.
- 데몬의 heavy 락·종목 락은 **같은 종목**이나 **무거운 잡끼리**만 직렬화한다. 계좌 단위로 묶는 장치는 없다.
- 집계 재료는 이미 있다. `repo._buy_amounts_today`·`pending_buy_amounts`·`today_order_amount` 가 살아 있는 BUY 와 pending 승인을 합친다.
- 그래도 빠지는 창이 다섯 있다.
  - **전송 중 주문**: 주문 행이 `place_order` 응답 **뒤**에 기록된다.
  - **승인 전환 중**: pending→approved 커밋 뒤 주문 전까지 집계에서 사라진다.
  - **전일 미체결**: 집계가 운영일 범위로만 잡힌다.
  - **부분 체결**: 잔량 대신 전체 금액을 센다. 보수적이라 위험은 작다.
  - **잔고 반영 지연**: 체결된 주문이 아직 잔고에 안 잡혔을 수 있다(추정).

### 안 비교
| 안 | 장점 | 남는 창·비용 |
|---|---|---|
| (a) 삽입 직전 재확인 | 기존 집계 재사용, 잠금 짧음 | **확인만 하고 커밋하면 안 닫힌다.** 확인과 예약을 한 트랜잭션에 써야 한다. 섹터·테마 한도 경쟁도 같은 검사에 넣어야 한다 |
| (b) 판정 전 예약 | 계좌 판정을 처음부터 직렬화 | 브로커 잔고 조회 동안 잠금이 길다. 소유자·만료·복구 관리가 붙는다 |
| (c) 현행 유지 | 비용 없음 | 다른 종목의 동시 통과·승인 전환 창이 남는다 |

### Codex 권고와 Claude 의견
- **Codex 권고**: (a) 를 보완한 "최종 재확인 + 원자적 예약" 이다. 순서는 다음과 같다.
  1. 잔고·시세는 트랜잭션 밖에서 읽는다.
  2. `BEGIN IMMEDIATE` 안에서 최신 예약을 다시 읽고, 현금·종목 수·섹터·테마 한도를 최종 검사한다.
  3. 통과하면 실행 키와 **예약 행**을 같은 트랜잭션에 쓰고 커밋한다.
  4. 커밋 뒤 `place_order` 를 부른다. 그동안에도 예약은 집계에 남는다.
  5. 응답이 오면 예약을 주문 행에 연결한다. 명확한 거부·미전송 실패만 예약을 푼다.
  6. 승인은 pending→전송 중 전환과 예약 승계를 원자적으로 한다.
  7. 응답 불명은 시간 만료로 풀지 않고 대조로 정리한다.
- **Claude 의견**: 동의한다. 처음 추천한 (a) 는 "확인만" 이라 창이 닫히지 않는다는 지적이 맞다.
- 다만 이 안은 주문 경로의 핵심을 고친다. executor `_place`·`approve`, repo 헬퍼의 내부 commit 정리, 원장 마이그레이션 1개가 필요하다.
- 그래서 **별도 주문 경로 PR(머지 전 사용자 확인)** 로 하는 것을 추천한다.
- 지금 위험의 크기: 데몬 안에서는 종목 락·heavy 락으로 창이 좁고, 브로커 현금 부족 거부가 최후 방어다. 다만 브로커는 종목 수·테마 한도를 막아 주지 않는다.

**결정 요청 7**: 원자적 예약 안으로 별도 주문 경로 PR 을 진행할지, 아니면 (c) 로 두고 실기에서 관찰할지.
